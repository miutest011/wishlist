# 测试工具

心愿单项目的自动化测试。没有任何依赖，不用装 npm、不用命令行，浏览器打开就能跑。
这套工具是从待办清单项目搬过来的，用法完全一样。

## 怎么用

**每次改完功能，打开 `tools/test.html` 看一眼。**

> ⚠️ **本地起服务器一定要用 `python3 tools/dev-server.py`**，别用 `python3 -m http.server`。
> 自带的那个不发缓存头，浏览器会自作主张缓存文件，导致你改完代码刷新看到的还是旧版本。
> 为此这里有三层防护：dev-server 明确禁止缓存、测试页加载脚本时自动带时间戳、
> `sw.js` 里本地 localhost 一律网络优先。

两种打开方式都可以：

- 直接双击 `tools/test.html`（少数要读项目文件的检查会显示「跳过」）
- 或者启动本地服务器后访问 `http://localhost:4173/tools/test.html`（推荐，所有检查都会跑）

页面顶部会显示汇总：

- **全部通过：N 条（已连跑两遍）** → 绿色，说明原有功能都没被改坏
- **N 条失败** → 红色，下面会写清楚是哪几条挂了、「期望值 / 实际值」分别是什么
- **N 条结果不稳定** → 黄色警告条，说明测试之间有状态泄漏
- **N 条没有断言** → 黄色警告条，说明有测试什么都没验证
- **跳过 N 条** → 灰色，当前环境跑不了的检查，换成本地服务器打开就会跑

### 运行器自带的三个机制

**① 每次都连跑两遍，比对结果。** 某条测试改了全局状态却没还原时，第一遍常常看不出来，
要等下一遍才露馅。两遍结果不一致就直接报出来。

**② 统计每条测试做了几次断言。** 一次断言都没做的测试会被标黄 —— 这种「假测试」
比没写测试更危险，它会让你误以为有保障。

**③ 跳过。** 有些检查只能在特定环境下跑（比如要读项目文件，双击打开时浏览器不让读）。
这时调用 `skip('原因')`，显示成灰色，既不算失败也不算假测试。
**别用 `skip` 绕开真正的失败。**

## 写完功能之后的固定动作

1. 补上对应的测试，打开 `tools/test.html` 确认全绿
2. **故意把代码改坏，确认测试会变红**，验证完恢复 —— 测试本身也要被测
3. 新踩的坑写进这个文件
4. 清掉测试数据（`localStorage` 和 IndexedDB），别把演示数据留给自己

## 文件说明

| 文件 | 作用 |
|---|---|
| `test.html` | 测试页面，打开它就会自动跑所有测试并显示结果 |
| `gallery.html` | 样板页：一页看全所有组件的所有状态，浅色深色并排。**调样式时打开它** |
| `test-runner.js` | 极简测试框架：`test()` 登记测试、`assert()` / `assertEqual()` 断言、`skip()` 跳过、`createMemoryStorage()` 和 `createMemoryMediaStore()` 提供假存储、连跑两遍比对结果 |
| `tests.js` | 心愿单的所有测试，以及 `setup()`、`click()` 这些公共工具 |
| `dev-server.py` | 本地开发服务器（不缓存任何文件） |
| `make-icons.py` | 生成应用图标（绿底 + 一张歪着的拍立得），改完颜色重跑即可 |

## 这个项目特有的坑

**别在测试里真的解码图片和视频。** 生成缩略图要用到 canvas 和 `<video>`，
在测试里又慢又不稳定（视频解码还依赖浏览器）。所以 `app.js` 把「处理媒体文件」
做成了可替换的依赖，测试里用 `useMediaProcessor()` 换成假的，直接返回一个假缩略图。
真正的解码逻辑在 `media.js` 里，那部分只能手动验证 —— 手动测的时候，
图片和视频都要各试一遍。

**`assertEqual` 不能用来比较 DOM 元素。** 它是按 `JSON.stringify` 比的，
元素会被序列化成 `{}`：拿两个**不同**的元素比永远「相等」，拿元素跟 `null` 比又永远「不等」。
「落点判定」那条测试因此连写两版都是假的 —— 看着绿，其实什么都没验。
判断有没有找到元素，用 `assert(x === null)` / `assert(x)`；
要比对具体是哪一个，就比它的 `dataset.dropId` 这种字符串。

**别在每次手指移动时重新量位置。** 拖拽时每来一个 `pointermove` 就把十几张卡片
重新 `getBoundingClientRect()` 一遍，浏览器每次都要重算布局，手指快速划过时
一秒几十次，画面就一顿一顿的。位置在开始拖的那一刻量一次存起来（用文档坐标，
自动滚动也不失效），移动时用 `requestAnimationFrame` 限流，一帧最多算一次。
**还有个更隐蔽的好处**：目标被高亮时会放大变形，每帧重量的话它的位置跟着变，
判定会在「命中 / 不命中」之间反复横跳，表现就是「明明盖住了却没反应」。

**长按期间页面会重画，闭包里抓着的元素会失效。** 拖拽是「按住半秒才开始」的，
这半秒里只要 `render()` 跑过一次（比如某张缩略图刚加载完），
当初按下时记住的那个元素就已经不在页面上了，量出来的位置和大小全是 0，
克隆出来的副本成了看不见的小点 —— 表现就是「怎么拖都放不进去」。
所以真正开始拖的那一刻要**按 id 重新找当前页面上的那一张**，量不到尺寸就干脆别拖。
查这个 bug 时，是靠把副本的内联 `style` 打进失败信息才看出来的（`width: 0px`）。

**加诊断代码本身会改变结果 —— 别把「加了诊断就变绿」当成修好了。**
查拖拽那条测试时，我只在测试里插了几句诊断（多读一次位置、多花几毫秒），
它就从红变绿了。真因其实是：跟手的副本是卡片克隆出来的，
继承了 `.card` 的 `transition`，判定落点时它还在半路上 ——
诊断带来的那几毫秒刚好让动画追上了，把 bug 盖住了。
**测试无缘无故变绿，要先怀疑自己动过的东西，而不是庆祝。**

**和布局有关的测试用「固定舞台」跑**：`setup({ stage: true })` 会把这一页钉在
视口左上角、自己带滚动。卡片的位置于是恒定，不受测试页滚到哪儿的影响 ——
否则运行器连跑两遍，两遍滚动位置不同，卡片有时贴着屏幕边缘，
同一条测试就会一遍过一遍不过。

**和布局有关的测试，先把元素滚进视野再操作。** 拖拽的落点是按「浮起来那张盖住了谁」
算的，要用到真实的位置和大小。测试页因此也加载了 `../style.css` —— 没有样式的话，
卡片没有正常的宽高，这类测试等于在另一个世界里跑。
另外贴着屏幕边缘拖会触发自动滚动，页面一滚，之前量好的坐标就对不上，
两遍跑出来的结果会不一样（运行器的「连跑两遍」正是这么把它抓出来的）。
所以 `dragOnto()` 会先 `scrollIntoView` 再量坐标。

**测试里的变量别和 `app.js` 的全局重名。** 写文件夹的测试时踩过一次：
测试里写了 `const items = [...]` 当种子数据，把 `app.js` 里那个同名的全局记录表盖住了，
于是 `assertEqual(items.length, 0)` 查的一直是种子数据，**这条测试等于没验东西**。
种子数据统一叫 `seeded`，真要检查结果就查 `storage`、或者用 `looseItems()`、`itemsIn()`
这些函数。同样要小心的还有 `folders`、`view`、`draft`。

**临时地址（`URL.createObjectURL`）用完要还。** 图片和视频从数据库里读出来是个 Blob，
要变成临时地址才能塞进 `<img>`。这些地址不还回去的话，内存会一直涨。
`app.js` 里统一记在 `objectUrls` 这个表里，删记录、离开详情页、重新挂载时都会清理。
